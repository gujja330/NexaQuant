04Daily pipeline

Every business day, both markets run the same deterministic flow. Snapshot → features → 11 models → ensemble → decision → portfolio → provenance → delivery. Every stage is idempotent per date; every output is auditable.

New in v3.2 (highlighted in indigo): stages 11 (Snapshot Ledger), 12 (Registry event-sourced), and 17 (MR-v1 Forward Validation). Stage 14 (Validators) is now driven by canonical-snapshot values instead of source-XLSX values that could be silently restamped.

10Canonical provenance layer · NEW in v3.2

Directive that shaped it: "One authoritative entry price and one authoritative prediction / exit-date chain, rather than independently reconstructing them downstream." All downstream consumers read from a single append-only canonical source. Historical evidence is never silently restamped.

What is canonical

  • Snapshot ledger · reports/delivery/prediction_snapshots.jsonl · immutable fields: prediction_id · market · ticker · prediction_date · entry_date · entry_price · source_close_date · source_dataset_version · canonical_signal
  • Registry · reports/research/opportunity_registry.jsonl · event-sourced · loader takes latest by ts_utc per pid
  • Trading calendar · derived from index parquets · validate_exit_chain enforces prediction_date < entry_date ≤ exit_date · exit_date ∈ calendar · exit_date ≤ asof
  • Quarantine audit · reports/delivery/quarantine_audit.jsonl · 4 events: QUARANTINE · RECONSTRUCT_PROPOSED · RESTORE · CANNOT_RECONSTRUCT

Permanent invariants (v3.2)

  • Entry price is copied from the immutable prediction snapshot. Downstream code cannot recompute or overwrite it.
  • Exit date must be an actual valid trading session after prediction date.
  • No weekend / holiday / backdated exit can enter the evidence layer.
  • Missing source data → quarantine, never substitution.
  • Re-running the pipeline must produce the same row.
  • Historical records are never silently restamped.
