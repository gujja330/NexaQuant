# AEGIS · Phase 2 · Identity Migration Contract

CEO 2026-09-01 · `GO P2 · DOCUMENT + EXECUTE` · this document is the
execution contract that governs the Phase 2 migration. The migration
proceeds deterministically against this exact specification. Any
deviation is a safety-stop.

## 1 · Canonical Position-ID Authority

**Authority**: `backend/research/opportunity_registry.py::make_opportunity_id`

```python
def make_opportunity_id(market: str, runner: str, ticker: str, created_date: str) -> str:
    r_tag = runner.upper().replace("_NEW","").strip()   # R1 | R2 | R3 | R?
    tk    = ticker.upper().replace(".NS","").replace(".BO","")
    mkt   = "IND" if market.lower() == "india" else "USA"
    ds    = created_date[:10].replace("-", "")
    sig   = hashlib.sha256(f"{mkt}-{r_tag}-{tk}-{ds}".encode()).hexdigest()[:6]
    return f"{mkt}-{r_tag}-{tk}-{ds}-{sig}"
```

**Format**: `{MARKET}-{RUNNER}-{TICKER}-{CREATED_YYYYMMDD}-{HASH6}`

**Examples**:
- `IND-R1-ITC-20260805-3cdd2a`
- `USA-R2-EIX-20260814-abc123`

## 2 · Why Registry Wins (E1 rationale)

- Registry (`opportunity_registry.jsonl`) is the append-only event-sourced
  ledger for every opportunity lifecycle. It's the single source of
  truth for `created_date`, `runner`, `market`, `ticker`, `status`.
- `make_opportunity_id` is deterministic: same inputs → same PID
  forever. Existing Registry PIDs are the authoritative canonical
  identity for every position they cover.
- The alternate emitters (see §3) were added later; none of them
  supersedes Registry's authority.

## 5 · Migration Rules

| Situation | Rule |
|---|---|
| Row already in canonical Registry format | ALREADY_CANONICAL · no-op |
| Row in `RUNNER-TICKER-MKT-DATE-hash` (Emitter 2) | Compute canonical via `make_opportunity_id(market, runner, ticker, created_date)` using the row's OWN `entry_date` / `Recommended` date. Replace `position_id`. Preserve original in `legacy_position_id`. Classification: DETERMINISTIC if row has valid runner + ticker + market + date · else AMBIGUOUS |
| Row in `MKT-RUNNER-TICKER-DATE-hash` but DATE ≠ Registry `created_date` (my earlier A1 migration bug) | Look up Registry entry by `(market, runner, ticker)`. If EXACTLY ONE match → use Registry's `opportunity_id` verbatim (DETERMINISTIC). If ZERO matches → INVALID. If ≥2 matches → AMBIGUOUS |
| Row in legacy `TICKER_MKT_DATE` (pre-A1) | Same as previous · Registry authoritative |
| Row with runner not in {R1, R2, SHADOW, MOMENTUM} | AMBIGUOUS |
| Row with unparseable date | INVALID |

## 8 · Identity Grain

Authoritative row-uniqueness key:

```
(market, position_id, runner, snapshot_date)
```

Where `position_id` is the canonical (Registry-format) PID.

Legitimate multi-observation on same (market, position_id, runner, date)
is EXPLAINED when the observations differ in Status, Rank, Confidence,
or Story (verified prior · pipeline emits multiple stamps per day). Only
bit-identical duplicate rows count as UNEXPLAINED violations.

## 9 · Historical Preservation

- **Every historical row survives** with its original PID recorded in
  the `legacy_position_id` column
- **Zero deletions**
- **Zero deduplications** — R1 and R2 observations are separate under
  A1; multi-observation same-day is preserved
- All non-identity fields (Status, Date, Rank, Confidence, P&L, Sector,
  Runner, Market, Ticker, etc.) are UNCHANGED

## 10 · `legacy_position_id` Retention

- `aegis_history.xlsx` already has a `Legacy Position ID` column (col C)
- `outcome_dataset.parquet` already emits `legacy_position_id` (see
  `outcome_dataset.py:339`)
- Migration preserves and populates these columns · never clears them
- After migration, `legacy_position_id` contains the pre-migration PID
  (for audit / provenance / reverse-lookup)

## 11 · Hard-Stop Conditions

Migration STOPS with non-zero exit if:
- Any row is classified AMBIGUOUS
- Any row is classified INVALID
- Any preflight sanity check fails (row count changes · unrelated
  field changes · runner mutation · market mutation · date mutation)
- Any post-migration reconciliation fails
- Registry lookup returns MULTIPLE canonical entries for the same
  `(market, runner, ticker)` at the same `created_date`
- A canonical identity collision arises where two DIFFERENT physical
  positions map to the same canonical PID

Ambiguous / invalid rows are emitted to
`reports/migration/pid_migration_ambiguous_20260901.jsonl` for manual
review.

## 13 · Pre/Post Migration Reconciliation Requirements

Pre-mutation:
- Snapshot row counts per file
- Snapshot per-column value distributions (Status, Runner, Market)
- Compute file SHA-256

Post-mutation:
- Row counts UNCHANGED
- Runner column values UNCHANGED (per-value counts)
- Market column values UNCHANGED (per-value counts)
- Status column values UNCHANGED
- Date column values UNCHANGED
- Rank / Confidence / P&L / Sector distributions UNCHANGED
- `legacy_position_id` populated on every migrated row (non-empty)
- Position ID distinct-count decreased by exactly the count of
  DETERMINISTIC mappings (collapsed to canonical)
- `aegis_final_reconciler.py::C7 + C9` pass with 0 UNEXPLAINED /
  0 unexplained-collision

## 14 · Idempotency

Migration MUST be idempotent:
- Running twice on already-migrated data → no additional writes
- Detection: if a row's `position_id` matches the canonical format AND
  the canonical PID matches what would be freshly computed from Registry,
  classification is ALREADY_CANONICAL · skip

Registry authority. All other architectural work happens in later phases.
